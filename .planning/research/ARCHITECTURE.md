## 1. Where Should Content Type Classification Happen?

### Recommendation: New `_run_content_planner()` function in `jobs.py`, called between `_ensure_catalog_outline()` and `ContentCreatorAgent.execute()`

**Exact insertion point — `src/scheduler/jobs.py` around line 1657:**

```
# CURRENT FLOW (lines ~1652–1663):
if seo_context:
    _ensure_catalog_outline(seo_context)          # ← AFTER this
    creator_task = seo_context.to_content_creator_task()
    content_result = await content_agent.execute(creator_task)
```

**Target flow after change:**

```
if seo_context:
    await _run_content_planner(seo_context, ai_provider)   # NEW — classify + outline
    creator_task = seo_context.to_content_creator_task()
    content_result = await content_agent.execute(creator_task)
```

### Why This Point — Not Earlier, Not Inside ContentCreatorAgent

| Option | Problem |
|--------|---------|
| Before SEOContext creation | SEOContext doesn't exist yet; the `selected_title` needed for classification isn't available until after HookOptimizer runs |
| Inside ContentCreatorAgent.execute() | Agent already receives its task dict; modifying the agent adds hidden side-effects and makes the data flow opaque. The agent should be a pure writer, not a planner. |
| Replace `_ensure_catalog_outline()` | That function is a fallback for catalog-context outlines. It should stay as the safety net; the new planner runs first and `_ensure_catalog_outline` only fires if the planner yields no outline. |
| New dedicated `ContentPlannerAgent` class | Valid for future, but the PROJECT.md explicitly prefers a planning step over a new agent class for Phase 1 (lower disruption). |

**Rationale:** At this point `seo_context.selected_title`, `target_keyword`, and all catalog context fields are fully populated. The AI provider is already instantiated (line 1636). No new instantiation needed — pass `ai_provider` in.

### Backward Compatibility Guarantee

The `_run_content_planner()` function should be wrapped in `try/except` that logs the error and continues. If it raises, the existing `_ensure_catalog_outline()` fallback already provides a catalog outline. Nothing downstream breaks.

```python
async def _run_content_planner(seo_context: SEOContext, ai_provider) -> None:
    """Classify content type and generate tailored outline. Non-fatal on failure."""
    try:
        from src.services.content.content_planner import ContentPlannerService
        planner = ContentPlannerService(ai_provider)
        await planner.plan(seo_context)
    except Exception as exc:
        logger.warning(f"ContentPlanner failed, using fallback outline: {exc}")
```

## 2. SEOContext DTO — Recommended Extension

### New fields to add to `src/models/seo_context.py`

```python
from enum import Enum
from typing import Optional, List

    Named ArticleContentType to avoid collision with existing ContentType in content_intelligence.py.
    """
    HOW_TO = "how_to"
    LISTICLE = "listicle"
    COMPARISON = "comparison"
    REVIEW = "review"
    PRICING = "pricing"
    GENERAL = "general"          # fallback when classification is ambiguous

class SEOContext(BaseModel):
    # ... all existing fields unchanged ...

    # ========== Content Planning (NEW) ==========
    article_content_type: Optional[ArticleContentType] = Field(
        None,
        description="LLM-classified article format. Set by ContentPlannerService before ContentCreatorAgent."
    )
    article_content_type_confidence: Optional[float] = Field(
        None,
        description="0–1 confidence score from the classifier call."
    )
    planned_outline: Optional[List[Dict[str, Any]]] = Field(
        default_factory=list,
        description=(
            "Ordered list of section dicts: {title, section_type, key_points, writing_notes}. "
            "Generated by ContentPlannerService and passed to ContentCreatorAgent via to_content_creator_task()."
        )
    )
```

### Why not reuse the existing `outline: Optional[ContentOutline]` field?

`ContentOutline` (in `content_intelligence.py`) is owned by the ContentIntelligence path and is already populated for CI-sourced topics. Overwriting it would destroy research-backed outlines. The new `planned_outline` is a simpler `List[Dict]` structure — lighter weight and not coupled to the existing `ContentOutline` Pydantic model.

### Update `to_content_creator_task()` to pass new fields

Add to the returned dict:
```python
"article_content_type": self.article_content_type.value if self.article_content_type else "general",
"planned_outline": self.planned_outline or [],
```

### No Alembic migration needed

`SEOContext` is a Pydantic DTO — it's not a SQLAlchemy model and has no database table. Adding new `Optional` fields with defaults is fully backward-compatible at runtime. Existing code that serializes/deserializes `SEOContext` via `.model_dump()` / `.model_validate()` will just ignore unknown keys on old payloads.

## 3. Combined vs. Separate LLM Calls

### Recommendation: Single combined LLM call with JSON mode

**Use OpenAI SDK 1.10.0 JSON mode** (`response_format={"type": "json_object"}`) — already supported by the existing `OpenAICompatibleProvider.client.chat.completions.create()` call pattern.

The prompt asks the LLM for both `content_type` and `outline` in one response:

```json
{
  "content_type": "how_to",
  "confidence": 0.92,
  "outline": [
    {"title": "What You'll Need", "section_type": "prerequisites", "key_points": ["..."], "writing_notes": "Use bullet list format."},
    {"title": "Step 1: ...", "section_type": "step", "key_points": ["..."], "writing_notes": "Numbered steps, include troubleshooting tip."},
    ...
  ]
}
```

**Why combined:**

| Concern | Single call | Two calls |
|---------|-------------|-----------|
| LLM cost | Half the tokens | Double the tokens |
| Latency | ~1–2s | ~2–4s (adds to per-article pipeline) |
| Coherence | Classifier informs outline in the same prompt | Outline prompt must re-pass classified type, risk mismatch |
| Error surface | One fallback path | Two failure modes |
| LangChain 0.1.4 relevant? | No — not used here | No |

**Why JSON mode over LangChain's `PydanticOutputParser`:**

LangChain 0.1.4 `PydanticOutputParser` works via prompt injection (`Format instructions: ...`) and regex-based extraction — it's fragile for nested structures. The existing codebase doesn't use LangChain's chain/parser abstractions at all (all agent calls go through `AIProviderInterface.generate_text()` → raw OpenAI SDK). Introducing LangChain output parsers here would be an inconsistent pattern.

Instead: use `response_format={"type": "json_object"}` directly on the `chat.completions.create()` call, then `json.loads()` + Pydantic validation. This matches how the rest of the codebase operates.

**Structured output implementation pattern:**

```python
import json
from pydantic import BaseModel, ValidationError

class PlannerOutput(BaseModel):
    content_type: ArticleContentType
    confidence: float
    outline: List[Dict[str, Any]]

async def _call_planner_llm(ai_provider, title: str, keyword: str) -> PlannerOutput:
    prompt = _build_planner_prompt(title, keyword)
    # Pass response_format via kwargs — AIProviderInterface.generate_text() passes **kwargs to create()
    raw = await ai_provider.generate_text(
        prompt,
        temperature=0.2,          # low temp for classification
        max_tokens=800,
        response_format={"type": "json_object"}
    )
    data = json.loads(raw)
    return PlannerOutput.model_validate(data)
```

Note: `response_format={"type": "json_object"}` is passed through the existing `**kwargs` in `OpenAICompatibleProvider.generate_text()`. This requires no changes to the AI provider layer. Verify the configured LLM model supports JSON mode (all gpt-3.5-turbo-1106+ and gpt-4-turbo-preview+ do; custom/local models may not — add a `try/except json.JSONDecodeError` fallback).

## 4. Per-Content-Type Writing Prompts — Organization Pattern

### Recommendation: Python dataclasses in a dedicated module (`src/services/content/content_type_templates.py`)

**Not Jinja2, not flat dict, not YAML/JSON config files.**

**Why Python dataclasses, not Jinja2:**

- Jinja2 is already in the stack (`jinja2==3.1.3`) and used for pSEO page factory (`src/pseo/`). Using it for writing instructions would work but creates unnecessary template file management overhead for what is essentially structured data.
- The existing prompt-building pattern in `ContentCreatorAgent._build_synchronized_prompt()` is pure Python string building — matching that pattern keeps consistency.
- Jinja2 templates are appropriate when the output structure varies significantly between types (HTML rendering). Writing instruction dicts are stable structured data.

**Why not flat `Dict[str, str]`:**

The existing `CONTENT_REQUIREMENTS` dict in `ProfessionalContentWriter` (which this subsystem partially overlaps) shows the limitation: it maps intents to flat boolean flags. Per-content-type templates need richer structure: H2 names, section ordering, writing mode per section.

**Recommended structure:**

## 5. Structured LLM Output Pattern for LangChain 0.1.x

### Important Clarification: LangChain 0.1.4 Is Not Used for LLM Calls in This Codebase

Despite being installed (`langchain==0.1.4`, `langchain-openai==0.0.5`), **LangChain is not used for actual LLM calls anywhere in the current pipeline**. All LLM calls go through `AIProviderInterface.generate_text()` → `OpenAICompatibleProvider` → raw OpenAI SDK `client.chat.completions.create()`.

This is confirmed by:
- `src/core/ai_provider.py` — direct OpenAI client, no LangChain chains
- `src/agents/base_agent.py` — `generate_text()` delegates to `ai_provider`, not a LangChain chain
- `src/scheduler/jobs.py` — no LangChain imports in content generation path

**Therefore:** Do not introduce LangChain's `PydanticOutputParser`, `with_structured_output()`, or `JsonOutputParser` for this feature. They would be an inconsistent dependency on top of a layer that isn't used.

### Recommended Pattern: JSON Mode via `response_format` + Pydantic Validation

**Confidence: HIGH** — OpenAI SDK 1.10.0 supports `response_format={"type": "json_object"}` (confirmed: shipped with gpt-3.5-turbo-1106 support, available in SDK since v1.x). The `**kwargs` pass-through in `OpenAICompatibleProvider.generate_text()` (line 74–80 of `ai_provider.py`) already forwards arbitrary kwargs to `chat.completions.create()`.

```python
# src/services/content/content_planner.py

import json
import logging
from typing import Optional
from pydantic import BaseModel, ValidationError, field_validator

from src.models.seo_context import SEOContext, ArticleContentType
from src.services.content.content_type_templates import CONTENT_TYPE_TEMPLATES

logger = logging.getLogger(__name__)


class PlannerLLMOutput(BaseModel):
    """Pydantic model for validating the LLM JSON response."""
    content_type: ArticleContentType
    confidence: float
    outline: list  # validated downstream

    @field_validator("content_type", mode="before")
    @classmethod
    def coerce_content_type(cls, v):
        try:
            return ArticleContentType(v)
        except ValueError:
            return ArticleContentType.GENERAL


class ContentPlannerService:
    """
    Classifies article content type and generates a tailored section outline.
    Called from jobs.py between _ensure_catalog_outline and ContentCreatorAgent.execute().
    """

    SYSTEM_PROMPT = """You are an SEO content strategist. Classify the article intent and 
generate a section outline. Respond ONLY with valid JSON matching this schema:
{
  "content_type": "<how_to|listicle|comparison|review|pricing|general>",
  "confidence": <0.0-1.0>,
  "outline": [
    {
      "title": "<H2 section title>",
      "section_type": "<step|list_item|comparison|verdict|faq|cta|prerequisites|etc>",
      "key_points": ["<point 1>", "<point 2>"],
      "writing_notes": "<specific instruction for the writer of this section>"
    }
  ]
}"""

    def __init__(self, ai_provider):
        self.ai_provider = ai_provider

    async def plan(self, seo_context: SEOContext) -> None:
        """Enriches seo_context in-place. Non-raising — logs and returns on any failure."""
        title = seo_context.selected_title or seo_context.topic_title
        keyword = seo_context.target_keyword

        prompt = self._build_prompt(title, keyword, seo_context)

        try:
            raw = await self.ai_provider.generate_text(
                prompt,
                temperature=0.2,
                max_tokens=900,
                response_format={"type": "json_object"}
            )
            parsed = PlannerLLMOutput.model_validate(json.loads(raw))

            seo_context.article_content_type = parsed.content_type
            seo_context.article_content_type_confidence = parsed.confidence
            seo_context.planned_outline = parsed.outline

            logger.info(
                f"ContentPlanner: type={parsed.content_type.value} "
                f"confidence={parsed.confidence:.2f} "
                f"sections={len(parsed.outline)}"
            )
        except (json.JSONDecodeError, ValidationError, Exception) as exc:
            logger.warning(f"ContentPlanner LLM call failed: {exc}. Outline will use fallback.")

    def _build_prompt(self, title: str, keyword: str, ctx: SEOContext) -> str:
        # Include template guidance so the LLM generates on-format outlines
        type_hints = "\n".join(
            f"- {t.value}: {CONTENT_TYPE_TEMPLATES[t].opening_instruction[:80]}..."
            for t in ArticleContentType if t != ArticleContentType.GENERAL
        )
        page_type_note = f"Page type context: {ctx.page_type}" if ctx.page_type else ""
        catalog_note = (
            f"Primary taxonomy: {ctx.primary_taxonomy_name} ({ctx.primary_taxonomy_type})"
            if ctx.primary_taxonomy_name else ""
        )

        return (
            f"{self.SYSTEM_PROMPT}\n\n"
            f"Title: {title}\n"
            f"Target keyword: {keyword}\n"
            f"{page_type_note}\n"
            f"{catalog_note}\n\n"
            f"Content type signals:\n{type_hints}\n\n"
            f"Generate 4–6 outline sections appropriate for this article's intent."
        )
```

### JSON Mode Fallback Strategy

If the LLM model doesn't support `response_format` (some custom/local models):

1. Catch `openai.BadRequestError` with error code `"invalid_request_error"` in `_call_planner_llm`
2. Retry without `response_format`, but append "Respond ONLY with valid JSON." to the prompt
3. Wrap `json.loads()` in `try/except json.JSONDecodeError` — extract JSON block via regex if needed: `re.search(r'\{.*\}', raw, re.DOTALL)`

## 6. Integration With ContentCreatorAgent — Writing Prompt Injection

The `ContentPlannerService.plan()` result reaches `ContentCreatorAgent` via `seo_context.to_content_creator_task()`. The agent's `_build_synchronized_prompt()` should pick up both:

1. `article_content_type` → selects the `ContentTypeTemplate`, injects `opening_instruction` and `closing_instruction`
2. `planned_outline` → replaces the current generic `## ARTICLE STRUCTURE` block when present

**Lookup pattern in ContentCreatorAgent:**

```python
from src.services.content.content_type_templates import CONTENT_TYPE_TEMPLATES
from src.models.seo_context import ArticleContentType

def _get_content_type_guidance(self, task: dict) -> str:
    ct_value = task.get("article_content_type", "general")
    try:
        ct = ArticleContentType(ct_value)
    except ValueError:
        ct = ArticleContentType.GENERAL
    template = CONTENT_TYPE_TEMPLATES.get(ct)
    if not template:
        return ""
    lines = [
        f"**Content Type**: {ct.value.upper()}",
        f"**Opening**: {template.opening_instruction}",
        f"**Closing**: {template.closing_instruction}",
    ]
    return "\n".join(lines)
```

When `planned_outline` is non-empty, use it to replace the section block. When empty (planner failed), fall back to the `outline` field from `ContentOutline` or the catalog outline from `_ensure_catalog_outline()`. This means the ContentCreatorAgent is always given the best available outline with zero hardcoded fallback logic needed in jobs.py.

## 8. Backward Compatibility Analysis

| Scenario | Impact | Mitigation |
|----------|--------|------------|
| `ContentPlannerService` LLM call fails | `article_content_type = None`, `planned_outline = []` | `_ensure_catalog_outline()` provides fallback; `ContentCreatorAgent` detects empty and skips content-type block |
| Model doesn't support JSON mode | `json.JSONDecodeError` | Retry without `response_format` + regex JSON extraction |
| Existing code reads `SEOContext` without new fields | New fields are all `Optional` with `None`/`[]` defaults | Pydantic ignores missing fields on deserialization |
| `to_content_creator_task()` consumed by other callers | Only called in `jobs.py` (verified by grep) | Adding new keys to the returned dict is non-breaking |
| `ContentCreatorAgent` receives task without new fields | New fields default to `None`/empty | Guard with `task.get("article_content_type")` checks |
